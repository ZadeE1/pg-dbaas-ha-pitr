Every decision that was open in revision 2 is now made. This is no longer a set of recommendations — it is the design. The one thing it deliberately does not specify is lifecycle: backups, point-in-time recovery, deletion, and secrets. Those are listed in §14 with the decision each one needs.

Locked

Cloudflare Mesh, Layer 3. Docker on host networking. A reserved port range with no proxy. Strict synchronous replication, so an acknowledged order exists on two machines. One gateway sidecar per app.

Deliberate costs

Host networking needs rootful Docker. Strict sync stops writes when one Pod is left. The DCS is pinned 1:1 to managers, so two host losses means every cluster goes read-only.

Backups and PITR. Cluster deletion. Secret distribution. Upgrades. The difference between a demo and a database you keep real orders in.

00  /  Start here

This section assumes you have never heard of any of this. It explains what you are building and why, lists everything you need before you begin, defines every word the rest of the document uses, and then walks through the first hour end to end. If you read nothing else, read this.

What you are building, in plain words

You want a database that keeps working when a machine dies, and a way to create new ones without becoming a database administrator. This is what that looks like from the outside.

You have three computers. On each one runs a small program called a manager. A manager does not serve your application and does not hold your data. It is a supervisor: it reads a list of what should be running, and it makes that true. That list lives in a shared database of its own — we call that the DCS, the Distributed Configuration Store — and every manager reads the same list, so they all agree without ever talking to each other.

The actual databases are called Pods. Three Pods, one on each machine, hold copies of the same data. One of them accepts writes. The other two follow along. That is replication, and it is the entire reason your site survives a dead machine: if the machine holding the writer dies, one of the others is promoted and takes over in about thirty seconds.

Your application never talks to a Pod directly, because the address of the writer changes whenever a machine dies. Instead a small program called a gateway sits inside your application's own container setup and does the looking-up. Your code points at localhost and is completely unaware. The gateway is a few hundred lines of configuration and holds no state of its own.

To create all of this you type one command into a terminal. You do not need a laptop plugged in afterwards. The program that ran the command is a control machine, and you can close it, switch it off, or throw it away. Nothing it did is stored on it.

Two settings that are off by default and will waste your afternoon

Cloudflare Zero Trust, before anything works
  • "Allow all Cloudflare One traffic to reach enrolled devices." Without this, your machines enrol successfully and then cannot see each other at all.
  • Split Tunnels must route the network's address range. By default the client sends ordinary internet traffic around Cloudflare and excludes the private range. Your machines will be on the network and still unable to reach each other.
  • Assign a unique address to each device. Every participant needs its own private address. Without it they collide and connections land on the wrong machine.
  • The device profile must use MASQUE, not WireGuard. Hostname routing and high availability are documented as not working under WireGuard. MASQUE is the default; just do not change it.

The words this document uses

That is the intended experience. Everything in the rest of this document is either the reasoning behind those steps or the behaviour when something goes wrong.

If you only remember three things

One. The only election in the system is which Pod is the writer, and it is settled by a shared store, not by the managers. Two. Your application talks to a gateway on localhost and never learns a Pod's address, so failover is invisible to it. Three. A write is confirmed to you only after it exists on two machines — so losing a machine cannot lose an order you were told was saved.

Abbreviations

Every abbreviation in this document, expanded once.

DCSDistributed Configuration Store. A tiny shared key-value store — here etcd — holding only metadata: who is primary, cluster settings, member list, desired state. Never your data.
WALWrite-Ahead Log. PostgreSQL's ordered record of every change. Replicas stream it to stay identical.
RTTRound-Trip Time. How long a request takes to reach the far side and come back. ~1-2 ms between your two VPS, ~25-30 ms to your home machine.
MTUMaximum Transmission Unit. Largest packet a link carries without splitting. Cloudflare Mesh uses 1381; a Docker bridge defaults to 1500. Mismatch is silent.
L3 / L7OSI network layers. Layer 3 routes whole packets and preserves long-lived connections end to end. Layer 7 understands protocols and terminates them. Replication needs Layer 3.
split-brainTwo Pods both believing they are the writer. Corrupts the dataset, and afterwards you cannot tell which was right. See §09.
PITRPoint-In-Time Recovery. Restoring a database to a chosen moment, not just to the last backup. Needs continuous WAL archiving.
pg_hba.confPostgreSQL's host-access file: which host, user and database may connect. The reason preserving source IPs in §05 matters.

01  /  The four things

Two corrections to the vocabulary before anything else, because the old words were doing damage.

Terminology

Not "stateless laptop." There is no such thing as a stateless machine. What you have is a control machine: a computer on the mesh that runs one CLI. It holds no state, is never needed at runtime, and nobody has to know it is online. Deleting it loses nothing. That is the property that matters, and it is a property of the design, not of a magical machine.

Not "router." The thing that fronts your database is a gateway, and it lives inside your application's own compose file, next to Medusa. Not on its own host, not holding a Pod. It is one more service in the stack you already run.

Control machine — where the CLI lives

A laptop, a workstation, a throwaway VM. It runs pgdbaas and it SSHes into your three hosts to bootstrap them. After bootstrap it can be closed, powered off, and forgotten. It comes back when you want to add a node, inspect a cluster, or destroy one. It is not a daemon and it is not in the data path.

Manager — one per host, permanently

A container on each machine whose only job is supervision: read what should be running, make it so, keep it so. Managers hold no cluster state, have no leader, and never coordinate with each other about who is in charge. A manager that dies takes its Pods with it and nothing else. A manager starting on a new host is a cold, empty container that converges.

Pod — spawned by a manager, many per manager

Patroni supervising one PostgreSQL instance, with its own data volume and its own DCS scope. Pods are disposable. A Pod's peers are the other Pods of the same logical cluster, wherever they live.

Gateway — one per application, inside your compose file

A small container beside your app that answers "which Pod is the primary of ecom-db right now?" and forwards TCP there. It holds no state. Your app points DATABASE_URL at localhost and never learns a single Pod address, never sees a failover, and needs no changes when the primary moves.

The load-bearing idea, restated

The only election in the system is per-Pod, inside Patroni, namespaced in the DCS. /service/ecom-db/leader and /service/billing-db/leader are unrelated keys. Everything else — managers, gateways, your control machine — has no vote and no lock.

02  /  Who tells the managers to create the Pods

This was the hole in the first draft, and you named it correctly. "Manager A creates the Pod" does not create a cluster. Something has to tell Manager B and C that they also owe the system a Pod, and it cannot be a conversation between managers — that is a quorum problem wearing a trench coat.

The answer is the one Kubernetes arrived at twenty years ago, minus Kubernetes: the DCS holds the desired state, and every manager is an independent reconciler that only acts on its own slice. There is no message, no leader, no coordination. Each manager polls a key, decides what it owns, and makes it true.

Why the lease is not optional

A node-id is written to disk at bootstrap and never changes. If you reimage a host, reinstall, or restore a backup, you can end up with a second manager presenting the same node-id. Without a lease, both would read the same spec entry, both would start a Pod named ecom-0, and both would mount the same directory. That is a corrupt data volume, discovered later. So: acquire /pgdbaas/v1/nodes/<id>/lease with a 15-second TTL before doing anything, renew it every 5 seconds, and exit immediately if you cannot get it. It costs a few lines and it is the difference between a fleet and a hazard.

What this deliberately gives up

There is no automatic rescheduling. If ecom-2's host dies, the CLI or a human moves it by editing the spec — you pgdbaas cluster move ecom-2 --to n2 and Manager n2 creates it. For three machines and a handful of databases that is the right trade: a human decides where data lives, and the system never surprises you by moving a volume onto a disk that is full.

03  /  Physical topology

Three manager hosts, each carrying one Pod of ecom-db and one etcd member. The application host is a fourth machine that is not part of the data path at all — it only holds the gateway sidecar.

04  /  The gateway

You described this well: it sits inside your Medusa compose file, you point your app at it, and it figures out the rest. The design question is only how it learns the member list, because everything after that is a health check.

Nothing about it is decided once. There is no seed list and no baked-in address. The gateway runs a resync loop forever: every 30 seconds it asks the managers for the current member list, diffs it against what it has, and reloads if anything changed. Between resyncs it is kept correct by health checks alone.

The important consequence: a failed resync is harmless. If every manager is unreachable, the gateway keeps routing correctly from what it last learned, because the health checks never needed a manager in the first place. It only means the gateway will not discover Pods that appear after it lost the managers.

Wiring it into your compose file

# docker-compose.yml, alongside medusa
services:
  db-gateway:
    image: ghcr.io/you/pgdbaas-gateway:latest
    environment:
      DB_CLUSTER: ecom-db
      # The only thing configured. Everything else - members, ports,
      # roles - is resynced from the managers every 30 seconds.
      DB_MANAGERS: "100.96.0.11:7000,100.96.0.12:7000,100.96.0.13:7000"
      DB_RESYNC_SECONDS: "30"
    ports:
      - "127.0.0.1:5432:5432"     # loopback only. never 0.0.0.0.
    restart: unless-stopped

  medusa:
    environment:
      DATABASE_URL: postgres://ecom:***@127.0.0.1:5432/ecom
    depends_on: [db-gateway]
The only configuration is which cluster, and where the managers are

Member addresses, ports, roles — all of that comes from the DCS on a loop. Move a Pod to a different host or a different port and the gateway picks it up within 30 seconds without you editing anything. That is the difference between a config file that is true on the day you write it and a config file that is quietly wrong by next month.

Bind it to loopback, not 0.0.0.0

The gateway's port is on the application host, not the mesh. Publishing 0.0.0.0:5432 would put your database on the public internet behind nothing but a database password. Keep it on 127.0.0.1 and let the mesh be the only way in.

05  /  Networking: why host mode solves it

The MTU problem I flagged in the first draft was real, and your instinct to reach for a different container runtime was the right instinct for the wrong reason. Switching to Podman would not have fixed it. The problem is not the runtime. It is that a container on a private bridge network has an MTU the overlay path cannot carry, and every container runtime inherits that.

The actual fix is to not have a bridge. With --network host the container is in the host's network namespace: no veth pair, no docker0, no DNAT, no masquerade. It binds the host's addresses directly, including the Mesh address Cloudflare already sized correctly.

What host networking does not break

The container still gets its own mount, PID, UTS, IPC and cgroup namespaces, its own root filesystem, and the default seccomp profile. It cannot see host processes or read host files it was not given. You are giving up one namespace, not six. Write network_mode: host out explicitly in the compose file so a reviewer can see exactly what was traded.

What this costs you, and how it is contained

Host networking means rootful Docker, which means the daemon needs root. Your instinct to avoid a root login was reasonable, so here is how the root is contained without you editing anything by hand.

The bootstrap script — the one you copy to each machine and run once, described in §10 — does all of it: it runs as root for a minute, and it leaves behind a control machine that is not root and has no shell. 

# Written by pgdbaas-node.sh. You never type this.
restrict,command="/usr/local/bin/pgdbaas-remote" ssh-ed25519 AAAA... pgdbaas-control

# The control machine can only say:
#   "enroll this host as node n2 and start the manager."
# It cannot open a shell, cannot forward ports, cannot become root.
# The script prints this line when it writes it, so you can see it happened.

So the sequence is: you read a short script, run it once as root on each host, and from then on the control machine is confined to a single fixed command on each box. That is a narrower control surface than a root shell, and the only thing you had to do was run one file.

06  /  The proxy chain, hop by hop

One INSERT from your app, tracing every layer. In host mode there is one fewer hop than the first draft had: there is no manager port-forward, because the Pod binds the host's Mesh address directly.

07  /  The replication path and the port budget

Replication is Pod-to-Pod, peer to peer, and it never touches the gateway or any manager. In host mode it is a direct connection from one host's Mesh address to another's, with the real source IP intact.

Ports: a reserved range, not a proxy

Host networking means every port a Pod binds is a port on the host, so two Pods cannot share one. The requirement is: never hardcode a port, always know which ones are free, and be able to change the scheme later without redesigning anything.

Reserve a range. Pick a block nothing standard uses — 21000-21999 — verify it at bootstrap, and record the base in the DCS. Pod k takes two ports from it: one for PostgreSQL, one for the Patroni REST API. There is no proxy and no port demultiplexer, so replication stays a single direct hop and the source address survives.

Two ports per Pod, not one. The REST port is the one that bites: Patroni's leader race calls restapi.connect_address on every other member. Omit it from the overlay and the cluster elects fine right up until the moment it needs to elect — and then it elects wrong, or hangs, under exactly the conditions you built it for.

Why a reserved range beat the fixed proxy window

A fixed-size window behind a manager-side demultiplexer sounds tidier — a small, enumerable port surface, immune to whatever else is on the host. It costs you two extra local TCP hops on every replication link, and it rewrites the source address, so pg_hba.conf could no longer name a host and your PostgreSQL logs could no longer tell you which machine connected. It also imposes a hard ceiling of Pods per host.

Reserving a range costs none of that. The surface is still fully enumerable — it is printed by pgdbaas status and stored in the DCS — and moving to a different range later is one value, not a redesign. In a three-host setup the window's main advantage was never worth those costs.

The one real cost, and how it shows up

A service you did not control can grab a port in the range after bootstrap. Re-checking the specific pair before every Pod create turns that from a mystery into an error message naming the port. That is the whole failure mode.

08  /  Leadership, demotion, and split brain

This is the mechanism that stops two Pods writing at once. It is the least intuitive part of the system, so here is all of it without jargon first.

The problem

Patroni keeps a leader lock in the DCS: the key /service/ecom-db/leader holds the name of the current primary, with a 30-second expiry. The primary renews it every ten seconds or so.

Now imagine the network between your hosts breaks. The primary can no longer reach the DCS, nor the other two Pods. From where it sits, it cannot tell the difference between:

  • "the shared store is down" — in which case it is probably still alone, and probably fine; and
  • "I have been cut off from everyone" — in which case the other two Pods may already have promoted a different primary, and both halves now believe they are the writer.

That second state is split brain: two Pods both writing to the same dataset. It corrupts the data, and afterwards you cannot determine which of the two was right. Both are confidently wrong and neither can prove it.

The answer

When the primary cannot renew its lock, it demotes itself: it stops accepting writes and goes read-only. The heading says "demotion, not a partition heal" because Patroni does not attempt to repair the broken network. It cannot, from one side of a partition. It just refuses to be the writer without proof, and lets the other half sort itself out — where a healthy quorum will already have elected a replacement, and the demoted node will come back and rejoin as a replica.

This is a trade, and the trade is deliberate

Availability traded for safety. A flaky network gives you an outage instead of data loss. The cluster goes read-only for up to thirty seconds, then either recovers on its own or a human forces a promotion knowing exactly what might be lost. The DCS exists for precisely this one reason: to make the decision possible.

Split-brain prevention is a demotion, not a partition heal

Patroni cannot tell "the DCS is down" from "I am partitioned away." It assumes the worst and demotes PostgreSQL to read-only the moment it cannot refresh the leader lock — a retry_timeout-graceful, ttl-worst-case shutdown.

This is the good news: a flaky overlay causes an outage, not data loss, and it takes every cluster sharing that DCS at once. Patroni's failsafe_mode relaxes it — the primary re-confirms itself against every known member over :21001 instead of trusting the DCS. Turn it on, but read its sharp edges first: it only covers some DCS error paths, and an etcdserver: no leader error has been reported to bypass it and force a demotion anyway.

09  /  Synchronous replication

This is the decision you made, and for an e-commerce store it is the right one. Here is exactly what it buys, what it costs, and the one setting that makes it cheap.

What "synchronous" actually means

A normal commit is: write the change locally, tell the client "OK", done. With synchronous_mode: on it becomes three steps:

  1. Write the change locally.
  2. Wait until at least one other Pod has flushed that change to its own disk.
  3. Only then tell the client "OK".

So when your app receives success, the change physically exists on two machines. If the writer's node dies one millisecond later, the other machine has the order. That is the entire guarantee, and it is exactly the failure you said you could not accept — a customer charged, and no order record.

The thing that is easy to misunderstand

Synchronous mode does not mean every standby is identical. At three Pods you have:

  • one writer (the primary),
  • one synchronous standby that is never behind — every commit is flushed to it before you are told "OK",
  • one asynchronous standby that may lag slightly, and is a spare.

Patroni maintains the synchronous role, so that standby is never the lagging one. The Pod that lags is the spare, and it is only ever touched when nothing better is available. So the shape you described — one writer, a reader that might be a touch behind, and the third being fine because it is a spare — is exactly what strict synchronous replication gives you. You get the shape and the guarantee.

Your hosts are not equidistant, and that matters

Step 2 above is a network round trip, so it lands on your write latency. And your three machines are not evenly placed:

  • Oracle VPS A to Oracle VPS B: ~1-2 ms. Same region, same private network.
  • Either VPS to your home machine: ~25-30 ms. Over the public internet, encrypted.

Patroni picks the synchronous standby by replication lag, not by distance, so it may choose the 30 ms peer when a 1 ms one is available. Tagging the far Pod nosync: true removes it from eligibility and forces synchronous replication onto the near one.

The same guarantee, about fifteen times less waiting

nosync changes nothing about durability. It changes only which network your writes wait on. For a catalogue you would not notice either version; for checkout, 2 ms instead of 30 ms is the difference between a snappy store and one that feels like it is thinking.

Crucially, nosync does not exclude a Pod from elections. It is still a valid failover target. It is only skipped when choosing who to wait on. And if the near standby dies, Patroni reassigns the synchronous role to the far Pod automatically, so writes stay safe — just slower for as long as that lasts. 

# patroni.yml on the Pod that should never be the synchronous standby
tags:
  nosync: true

# Nothing else changes. If you ever move both VPS to one machine and the
# home node to the other, flip which Pod carries the tag. One line.

The curve: 3 → 2 → 1

The rule underneath all of it: a write is only allowed if a copy lands on a second machine before you are told "OK".

The two behaviours that surprise people, stated plainly

1. The cluster can sit read-only with a live Pod. If the writer dies and the only survivor is an asynchronous replica, Patroni will not promote it automatically — because it cannot prove that Pod has every committed write. So you get a running Pod that is refusing to write, and nothing appears broken. This is the design working: the alternative is promoting a Pod that silently dropped your last orders. When you want it anyway, pgdbaas failover --force promotes it and tells you what may be lost.

2. Strict mode is not atomic, and one config value closes most of the gap. If a backend is cancelled while waiting for the replication acknowledgement — a client-side statement timeout, say — the commit can already be durable locally while your app is told it failed. The practical fix is boring: keep every client statement_timeout comfortably above your worst-case commit time. With the nosync tag, that means above about 30 ms, so 5 seconds is a safe choice and 25 milliseconds is a bug waiting for a slow evening.

If you ever want reads from the synchronous standby to be guaranteed current rather than merely flush-current, set synchronous_commit: remote_apply. It makes the primary wait until the standby has replayed the change into its data files, not just written the log. More latency, stronger read guarantee. The default on is right for your case.

The row people skip: two Pods

Two Pods is not "half degraded". It is the safety net is gone. Writes still work and are still safe, but there is no spare: a writer failure is now a genuine outage until a node comes back, rather than a thirty-second blip. Worth knowing before you are one node down and surprised.

10  /  Bootstrapping with one script

You want one command that takes a list of hosts and ends with a working three-node cluster, and you do not want to be hand-editing authorized_keys or any other config on three machines. Fair. The shape is: a single script you copy to each machine and run once. 

# on each of the three hosts, as root:
scp pgdbaas-node.sh you@10.0.0.4:/tmp/
ssh you@10.0.0.4 'sudo /tmp/pgdbaas-node.sh --id n1'

# That is the whole install. The script:
#   1. prints every action it is about to take, and waits for you
#   2. installs cloudflare-warp and enrols this host as a Mesh node
#   3. installs and configures Docker
#   4. scans the reserved port range and reports anything already taken
#   5. writes /etc/pgdbaas/node.json  { id, mesh_ip }
#   6. installs the manager and its control socket
#   7. adds the control machine's key, restricted to one fixed command
#   8. is idempotent - safe to re-run after a failure or a reinstall

Then the control machine does the rest:

  1. Pin by node-id, not by IP. The script writes the id to disk at first boot and the spec keys off that, so DHCP or a changed address does not reshuffle your cluster.
  2. Install the SSH restriction as part of the script, not by hand. The control machine can only ever run one fixed command on a host — never open a shell, never forward a port. You never touch this file; the script writes it and shows you the line it wrote.
  3. Verify before you trust. After install, the control machine checks the Mesh route, the MTU, clock skew, and the DCS quorum, and refuses to continue with the name of the check that failed.
On the trust question, honestly

A restricted key means the remote side can only do one thing. A script you run means you trust the whole script. That is a real difference, and the mitigation is not clever — it is that the script is short, it lives in this repository, and step 1 makes it print what it is about to do. Read it once, run it, and the control surface is contained.

The command surface, so far

# --- bootstrap, run from the control machine -------------------------
pgdbaas node add --host 10.0.0.4 --user deploy --id n1
pgdbaas node add --host 10.0.0.5 --user deploy --id n2
pgdbaas node add --host 10.0.0.6 --user deploy --id n3

pgdbaas cluster create ecom-db --nodes n1,n2,n3 --pg 16 --env dev

# --- everyday -------------------------------------------------------
pgdbaas status                       # one screen: nodes, clusters, roles, lag
pgdbaas doctor                      # mesh route, MTU, clock skew, quorum, volumes
pgdbaas psql ecom-db                # opens a shell on whatever is primary
pgdbaas topology ecom-db            # who is primary, who is streaming, how far behind
pgdbaas switchover ecom-db --to ecom-2

# --- changing the fleet ---------------------------------------------

pgdbaas node doctor n2              # drain a host for maintenance

Note what is missing, on purpose: nothing in that list requires the CLI to be running for the database to be up. pgdbaas status is a convenience, not a dependency.

11  /  Failure drills

Design these as tests. Each has a specific correct behaviour, and the ones marked are where this design will actually surprise you.

Kill thisExpectedWhere it goes wrong
The primary Pod Leader lock TTL (30s) expires, Patroni promotes the synchronous standby — which by construction has every committed write. The gateway flips within ~2s of the new primary answering 200. No acknowledged order is lost, which is the entire point of §09. Gateway holding a stale backend. HAProxy must drop sessions on mark-down, not just stop routing new ones.
The standby, primary alive Patroni reassigns the synchronous role to the remaining replica and writes keep flowing. If that replica is the home machine, write latency temporarily becomes ~30ms until the near node returns. A client statement_timeout set below the new commit time. Transactions start failing — see the sharp edge in §09.
One host Two Pods left, still reading and writing (see §09). The cluster loses its spare, so a writer failure is now a real outage rather than a blip. A new manager on a replacement host converges and you move the Pod with cluster move. Nothing automatic here by design. A human decides where data lives.
Two hosts etcd loses quorum, every cluster demotes to read-only within retry_timeout + ttl. This is the availability cliff. This is the one real structural weakness. etcd is pinned 1:1 to managers. Break that coupling — see §12.
The gateway The app's connections fail. Recreate the gateway, or use a second one. The cluster is completely unaffected. If the app has only one gateway and no pool retry, the outage looks like a database outage. It isn't.
The application host Nothing. It is a client. The cluster keeps running and you lose only the storefront. Nothing. This is a feature and worth testing so you trust it.
Mesh for 60s Patroni in every cluster loses the DCS and its peers, primaries demote. Nothing corrupts, everything goes read-only, and it recovers on its own. With failsafe_mode on, a primary that can still reach all its Pods keeps its lock. Decide deliberately.
One Pod's network, silently Patroni marks it down, gateways stop selecting it, it rejoins from the base backup. A TCP-checked proxy would keep sending writes to a partitioned primary — this is why the REST check is mandatory. Any component that health-checks the data port instead of the REST /primary endpoint will eventually write to a replica or a zombie.
A Pod that was down comes back It rejoins as a replica — it is not promoted, and it does not become primary just by returning. If its WAL is a clean subset of the primary's it just resumes streaming. If it diverged, Patroni either rewinds it back or wipes and re-clones from a base backup. Either way, once caught up it is a full candidate for future elections. Your instinct — "it should forget the bad data and get fresh data" — is exactly right, and Patroni does it without being asked. The cost is a base backup over the mesh, so a large database rebuilding onto the home machine is the slow case. wal_log_hints: on is what makes the rewind path fast instead of forcing a full re-clone.
A host reboot Everything comes back. Postgres is only ever started by Patroni. Anything that can also start Postgres — a stray unit, a compose restart policy — is a split-brain waiting to happen.
Reimage a host, keep the old id The new manager cannot take the node lease and exits with a clear error. You enrol it as a new node instead. Without the lease: two Pods named the same thing on one volume. This is the failure the lease in §02 exists to prevent.

12  /  HAProxy, concretely

The gateway's entire job. Note that this is the same config whether the gateway runs in your app's compose file or on a host of its own. 

global
  maxconn 4096
  # no aggressive idle timeout: an e-commerce worker can hold a
  # connection for minutes across many small transactions

defaults
  mode  tcp
  log  global
  retries 2
  option  dontlognull
  timeout connect   4s
  timeout client    30m
  timeout server    30m
  timeout check     3s

# ---------- writes : only the current primary passes this check ----------
listen pg_write
  bind 127.0.0.1:5432
  balance first                     # only one server is ever UP; this costs nothing
  option httpchk GET /primary
  http-check expect status 200

  # the two settings that stop a write landing on a demoted primary
  on-marked-down shutdown-sessions
  default-server inter 2s fall 3 rise 2 on-marked-down shutdown-sessions

  server ecom-0 100.96.0.11:21000 check port 21001 maxconn 200
  server ecom-1 100.96.0.12:21002 check port 21001 maxconn 200
  server ecom-2 100.96.0.13:21004 check port 21001 maxconn 200

# ---------- reads : replicas only, and only ones that are actually caught up ----
listen pg_read
  bind 127.0.0.1:5433
  balance leastconn
  option httpchk GET /replica
  http-check expect status 200
  http-check send meth GET uri /readiness?lag=16777216
  on-marked-down shutdown-sessions
  default-server inter 2s fall 3 rise 2 on-marked-down shutdown-sessions
  server ecom-0 100.96.0.11:21000 check port 21001
  server ecom-1 100.96.0.12:21002 check port 21001
  server ecom-2 100.96.0.13:21004 check port 21001

listen stats
  bind 127.0.0.1:7001
  stats enable
  stats uri /
Why option httpchk and not a TCP check

A TCP check to 21000 passes on the primary and on every replica, because a hot standby accepts connections. You would load-balance writes across the whole cluster and watch the app throw cannot execute INSERT in a read-only transaction after every failover. Patroni's REST API exists so a proxy can ask the question a socket cannot: are you the leader right now, and do you still hold the lock?

13  /  Backup and point-in-time recovery

Until this section existed, the system was highly available and completely unprotected — a bad migration or a dropped table would have taken the database with it, redundancy and all. This is the design that closes that gap.

The tool, and why

WAL-G (a single static binary) writing to a Cloudflare R2 bucket. Three properties decided it:

  • No backup server. WAL-G talks to object storage directly. That means no extra machine to keep alive — which matters more than usual here, because another always-on node would be another vote in the DCS quorum and another thing that can take your clusters down.
  • Configuration is environment variables. The manager generates them per Pod. There is no config file for you to hand-edit, which was an explicit requirement.
  • It can prove its own backups are restorable. wal-verify walks the archive and reports any segment that is missing, which is precisely the failure that silently turns "point-in-time recovery" into "I can only go back to Tuesday."

I looked hard at pgBackRest, which has the better feature story — page-level incrementals, parallel restore, and real repository verification. Two things ruled it out. It wants to co-locate with the database host or reach it over SSH, which is a poor fit for config this system generates. And in April 2026 its sole maintainer archived the entire project; a sponsor coalition revived it within a week, so it is healthy now, but I did not want a single-maintainer dependency sitting in the critical path of "get my database back." Barman needs a dedicated backup server, which defeats the first point above.

Nothing to configure, on purpose

If enabling backups is a separate step you have to remember, you will forget it. So pgdbaas cluster create provisions them, and the defaults are the ones you would have picked:

DefaultValueWhy this one
WAL archivingcontinuous, from every PodThis is what makes point-in-time recovery possible at all. RPO is measured in seconds.
Full backup03:00 dailyRestore time is roughly proportional to how much WAL you replay after a full.
Delta backup04:00 dailyCheap insurance, and it shortens the worst-case replay.
Retention7 fulls, 14 days of WALTwo weeks back is long enough to notice a slow problem and still fix it.
Encryptionon, key off the DCSA leaked bucket should not be a leaked database.
Verificationafter every fullFree, automatic, and the only way to know.

Everything is still changeable, but with a key=value form on the command that owns the thing, rather than a config file: 

pgdbaas cluster set ecom-db backup.retention=30d backup.schedule="0 3 * * *"
pgdbaas backup now ecom-db          # take one immediately
pgdbaas backup list ecom-db         # what exists, how big, how old
pgdbaas backup prune ecom-db        # dry run. prints the plan, deletes nothing
Encryption key handling, briefly

Generated once, printed once so you can put it in a password manager, and stored on the three managers — not in the DCS, because the DCS is readable by every Pod in every cluster. If all three hosts are lost, the backups are still readable: by you, with that one passphrase.

The one screen that answers "am I safe?"

This is the most valuable thing in the whole section. Most people discover their backups are broken at restore time, which is the worst possible moment. So backup health is a first-class line in pgdbaas status, and it goes red when it should: 

$ pgdbaas status

  ecom-db       running   primary ecom-1 (VPS B)   lag 0s
    last full backup     6h ago     full 03:00        ok
    last WAL archived   40s ago                       ok
    PITR window          14 days (since 16 Sep)      ok
    last verified        9h ago     restore drill     passed
    recoverable to       any moment in the last 14 days
    size in bucket       2.1 GB                      ~$0.03/mo

  billing-db     running   primary ecom-... (home)
    last full backup     31h ago                     LATE
    last WAL archived   6h ago                       STUCK
    PITR window          4 days (since 26 Sep)      DEGRADED
    last verified        never                       never run
    size in bucket       840 MB

A stuck archive is the loud one. It means the window is closing right now, and it is the failure that turns into a disaster if you find out a week later. pgdbaas doctor names the cause, and pgdbaas backup repair ecom-db fixes the common ones (a rotated credential, a bucket that stopped accepting writes, a Pod that came up with the wrong env).

Make it shout without a monitoring stack

You do not have Prometheus here, and you should not build one to find out your backups are broken. Put a systemd timer on the control machine: pgdbaas doctor --quiet every fifteen minutes, appending to a log, plus one line that mails you on failure if you want. And because the gateway already runs a health endpoint for your app, it can expose /backup-status — so an external uptime check covers this too.

A restore is a create, not a destroy

This is the single most important decision in the backup design, and it is a UX decision as much as a technical one.

The intuitive version of a restore — wipe the cluster, load the backup, start serving — means that if you pick the wrong timestamp, you have just destroyed the data you were trying to save. That is how a bad afternoon becomes a bad month.

So the default creates a new cluster alongside the old one. Nothing is destroyed until you deliberately destroy it: 

# what you will actually type, in the moment you need it
pgdbaas backup history ecom-db                  # see what exists
pgdbaas restore ecom-db --to "1 hour ago" --as ecom-recovered
# ...read the output, check the row counts, then:
pgdbaas gateway point ecom-recovered
# ...and days later, once you are sure:
pgdbaas cluster delete ecom-db

# the delete refuses while a gateway still points at the cluster,
# so you cannot lose a database to a typo in a name

Redundancy, honestly

Three Pods on three hosts is not redundancy for a backup, because every one of those hosts depends on the same overlay, the same home connection, and the same credentials. So the backup gets its own layered answer, and it is worth being clear about which tiers are load-bearing and which are optional.

TierWhatSurvivesCost
1 — always on WAL-G → R2, your own account. Eleven nines of durability, offsite from home, no egress fees. Host loss, home connection loss, Pod loss, a bad migration, an accidental DROP. ~$0.015/GB-month. Negligible at catalogue scale.
2 — always on Nightly compressed pg_dump → a second R2 bucket in a second Cloudflare account. Deliberately a different tool and a different login. WAL-G breaking, this account being locked out or compromised, a retention bug, silent corruption in the WAL archive. Negligible. One bucket and one scheduled job.
3 — optional Mirror the dump to a second provider. The only tier covering "Cloudflare is having a bad day at the exact moment you need a restore." A Cloudflare-wide outage, including the storage API being unreachable mid-recovery. ~$6/TB/year, plus egress when you actually restore.
4 — not recommended A local copy on each of the three hosts. Nothing that matters. All three depend on the same mesh and the same power supply. Wasted disk, and a false sense of safety.
What tiers 1 and 2 together actually buy you

Losing your Cloudflare account, your bucket, or your backup tooling: covered. Cloudflare having a regional outage while you are mid-restore: not covered without tier 3 — though the window is narrow, because a storage outage does not take your database down, only your ability to recover during it.

I would start on tiers 1 and 2, and add tier 3 the first time you find yourself rehearsing a restore and notice you are holding your breath for a provider. That is a reasonable trigger, and it can be deferred.

The retention footgun, designed around

After a major PostgreSQL upgrade the internal timeline number resets, and ordering by name can decide your newest backups are old and delete them. That is a real documented behaviour, and it bites on exactly the week you upgraded.

The fix is structural: one storage path per major version (pgdbaas/ecom-db/pg16/, pgdbaas/ecom-db/pg17/), so retention never sees two timelines mixed. Pruning is a dry run by default, and the manager refuses to prune a history with fewer than two fulls.

What this does not cover

  • Recovery point. With continuous archiving it is the gap between WAL segments — seconds in practice. A restore is bounded below by your last full plus the WAL replay, and the monthly drill is what gives you the real number instead of the imagined one.
  • Recovery time. Proportional to database size and to the mesh. A restore pulling gigabytes from R2 down to your home machine is slower than the same restore to an OCI box. Measure it during the drill rather than discovering it.
  • Logical corruption. Backups faithfully preserve a dropped table; nothing in a physical backup design can tell you a row was deleted by mistake. Catching that needs dump diffs or checksums on critical tables — a separate project.
  • A stolen passphrase. Encryption at rest makes a leaked bucket useless, but whoever holds the passphrase can read everything. Treat it like the database password.
The part that actually matters

Everything above is plumbing. What protects you is the automatic verification after every full backup, and a broken archive turning a line in pgdbaas status red instead of remaining a surprise. A backup you have never restored is a hypothesis, not a backup — and because R2 has no egress fees, testing that hypothesis costs a few minutes of disk and nothing else.

14  /  Lifecycle: the rest

Backup and recovery are designed. These remain, and each is smaller than the section above.

SurfaceDecision it needs
Deletion Two-phase and hard to do by accident. pgdbaas cluster delete ecom-db refuses while any gateway still points at the cluster, because a cluster name is load-bearing in a live app's config. Then it asks you to type the name. Only after that does it destroy Pods, volumes, and backups — the last behind a separate flag, since orphaned backups cost money and hide the fact that a database ever existed.
Secrets Database passwords cannot live in the DCS, because every Pod in every cluster can read it. Each Pod gets a generated credential the manager hands out once at creation; the superuser password is sealed with a key held only on the managers. The backup encryption key follows the same rule.
Upgrades PostgreSQL major upgrades and manager upgrades both want a drain: stop placing Pods on a host, take it out, upgrade, put it back. A major upgrade is also when the storage path changes in this section, and the moment the restore path deserves retesting before you need it.
Decoupling the DCS The availability cliff in §11. A fourth always-on machine holding only the third etcd vote is the cheapest fix — it need not be powerful, just never off. Note that the backup design deliberately adds no such node.

15  /  Open questions

Most of what was open in revision 2 is now closed. These are the ones that remain, and they are all answerable without redesigning anything.

  1. Backups, and when. The one question that actually matters. Nothing in this document protects you from a bad migration, an accidental DROP, or a corrupted volume. Until WAL archiving exists, the cluster is highly available and completely unprotected. See §13.
  2. Does the application host stay put? The gateway reaches the Pods over the mesh, so whatever runs Medusa has to be a Mesh participant. Right now that is assumed to be a server. If you ever want to run the storefront from a laptop, the laptop gets enrolled and the gateway comes with it — the design survives, but the mesh node count grows.
  3. How many clusters will this carry? One DCS holds hundreds of clusters by namespace, so this scales fine in principle. But each Pod takes two ports from the reserved range, and a host running eight Pods has a port map worth checking against pgdbaas status before you lose track of it.
  4. Is nosync still pointing at the right Pod in six months? It is a tag expressing a physical fact — that one host is far away. If you move the VPS, or add a fourth node next to them, the tag should move. Consider having pgdbaas doctor measure actual RTT between hosts and tell you when the assumption no longer holds.
  5. What is your actual catalogue size? A re-clone is a base backup over the mesh. At ~2 ms between the VPS that is fast; a large database rebuilding onto the home machine at 30 ms will take noticeably longer. Worth measuring before you need it.
